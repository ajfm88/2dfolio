# AI Workflow Rules

These are rules, not guidelines. Follow them literally.

## Approach

Build Coral Corsairs incrementally, one unit at a time, against a spec file.

- The build order is `context/specs/00-build-plan.md`. Do not work out of order.
- Each unit has a spec at `context/specs/NN-<name>.md`. Read it before writing
  code and implement exactly what it says.
- If a unit has no spec file yet, write the spec first and get it approved. Do not
  start implementing from a one-line request.
- The context files define what to build, how to build it, and where the project
  stands. Implement against them. Do not infer product behaviour from scratch, and
  do not copy behaviour from the Python references unless a spec says to port it.

## Scoping Rules

- Work on **one unit at a time**. Finish it, verify it, mark it complete, then move.
- Prefer small verifiable increments over large speculative changes.
- Do not combine unrelated system boundaries in one step. `core/`, `level/`,
  `game/`, `maker/`, `ui/` and `storage/` are separate concerns.
- **Do not build for a future unit.** No hooks, no abstraction layers, no config
  options for a feature that is not being built now.
- **Do not refactor code you were not asked to touch.** If a refactor is needed,
  say so and stop; do not fold it into an unrelated unit.
- Install a dependency only in the unit where it first unlocks real behaviour.
  Never install "while we're here".
- Anything in the Out of Scope list in `1-project-overview.md` is not built, not
  scaffolded, and not suggested.

## When to Split Work

Split an implementation step if it combines any two of:

- Engine changes and gameplay changes.
- Canvas rendering changes and DOM UI changes.
- Level schema or codec changes and anything that consumes them.
- A new entity type and a change to how entities are registered or spawned.
- Touch input handling and desktop input handling, when the behaviour differs.
- Asset pipeline changes and runtime code that reads the new output.

If a change cannot be verified end to end in a single run of the game, the scope is
too broad. Split it.

## Handling Missing Requirements

- **Do not invent product behaviour.** If a spec does not say what happens, it is
  not defined yet.
- If a requirement is **ambiguous**, resolve it in the relevant context file first,
  then implement. Update the file in the same change.
- If a requirement is **missing**, add it as an open question in
  `6-progress-tracker.md` and either ask, or implement the smallest defensible
  behaviour and record the assumption in the same file. Never leave the assumption
  undocumented.
- If a requirement **contradicts an invariant** in `2-architecture.md`, stop.
  Report the conflict. Do not weaken an invariant to make a feature fit.
- If a bug is found that is outside the current unit, log it in
  `7-current-issues.md` and keep going. Do not fix it inside an unrelated unit.

## Protected Files

Do not modify these without an explicit instruction that names them:

- `reference/**` — **read-only, always.** Gitignored source material:
  - `treasure-hunters/` — the Pixelfrog art pack.
  - `pirate-maker/` — Clear Code's editor project.
  - `super-pirate-world/` — Clear Code's platformer project and the CC0 audio.
- `public/assets/**` — generated by `npm run assets`. Change
  `tools/asset-manifest.mjs` and regenerate; never hand-edit output.
- `src/data/atlas.json` — generated. Same rule.
- `context/README.md` — the methodology playbook. Reference material.
- Any lockfile — changed only as a side effect of an intentional install.

Never copy a reference project's file into `src/` and edit it in place. Port the
idea, write the JavaScript, and cite the source in a comment.

## Keeping Docs in Sync

Update the relevant context file **in the same change** whenever implementation
alters:

| What changed                                   | Update                       |
| ---------------------------------------------- | ---------------------------- |
| Feature scope, in or out                        | `1-project-overview.md`      |
| Folder boundaries, schema, storage keys, invariants | `2-architecture.md`     |
| Colour tokens, typography, component conventions | `3-ui-context.md`           |
| Conventions, naming, rejected patterns          | `4-code-standards.md`        |
| Workflow itself                                 | `5-ai-workflow-rules.md`     |
| Anything meaningful, every time                 | `6-progress-tracker.md`      |
| A defect found or fixed                         | `7-current-issues.md`        |

If the level schema changes, `format` is incremented and a migration path is written
before any code reads the new shape. Saved levels are never silently invalidated.

## Before Moving to the Next Unit

All of these must be true:

1. The unit works end to end within its defined scope, verified by running the game
   — not by reading the diff.
2. No invariant in `2-architecture.md` is violated.
3. No placeholder, stub, mock or `TODO` remains in the code this unit touched.
4. `npm run build` passes with no errors.
5. `npm test` passes, and any pure module added in this unit has tests.
6. No console errors or warnings during a normal run of the affected screens.
7. If the unit touched input, layout or the maker: verified at a phone-sized
   viewport **and** a desktop viewport, in both orientations, with touch emulation
   on and off.
8. If the unit touched the level schema, codec or autotiler: an existing saved level
   still loads and plays.
9. `6-progress-tracker.md` records the unit as complete, with any decisions made.
10. `7-current-issues.md` records anything found but deliberately not fixed.

## The Three Prompts

Every unit runs the same cycle.

**Implement**
```
Read context/specs/NN-<name>.md.
Mark it in progress in context/6-progress-tracker.md.
Implement it exactly as specified. Do not go beyond the scope of this unit.
```

**Correct**
```
The <specific element> does not match the spec.
Expected: <what the spec says>.
Current: <what was built>.
Fix only this. Do not change anything else.
```

**Close**
```
Implementation is complete and verified.
Mark unit NN complete in context/6-progress-tracker.md.
```

## When Stuck

If the same problem survives two attempts, stop coding.

1. State plainly what was tried and what happened.
2. Say which assumption is most likely wrong.
3. Propose the smallest experiment that would confirm or kill it.

Do not attempt a third variation of the same fix, and do not widen the change to
"work around" it.
